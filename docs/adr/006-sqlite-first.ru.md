# ADR-006 — SQLite для первого развёртывания

**Статус:** принято

## Контекст

Один процесс приложения, один VPS на 2 ГБ, несколько операций записи на
обращение и один оператор. Реалистичный пик — несколько писем в минуту.

## Решение

SQLite через SQLAlchemy, схема управляется Alembic. Журналирование WAL, таймаут
ожидания блокировки 30 секунд и `foreign_keys=ON`, включаемый для каждого
соединения.

## Рассмотренные альтернативы

- **PostgreSQL сразу.** Второй контейнер, больше памяти на хосте с 2 ГБ,
  резервное копирование, которое надо продумать, и никаких возможностей, нужных
  этой нагрузке. Решение принято осознанно, а не по незнанию: путь миграции
  понятен и в основном подготовлен.
- **Управляемая база данных.** Стоимость и задержки без выигрыша при таком
  размере.
- **Файлы или JSON.** Нет транзакций, а ADR-005 целиком на них опирается.

## Последствия

- Резервная копия — это копия файла, но снятая через штатный API онлайн-бэкапа
  SQLite, а не `cp`, поэтому живая база никогда не захватывается в середине
  записи.
- `foreign_keys=ON` важнее, чем кажется: по умолчанию SQLite игнорирует внешние
  ключи, из-за чего ограничения из миграций были бы декоративными. Включение
  сразу же выявило настоящую ошибку порядка удаления в скрипте сброса
  демонстрационных данных.
- Потолок — один писатель. Это главная причина, почему система рассчитана на
  один узел, и именно это честное ограничение указано в README.
- Переход на PostgreSQL — это смена URL, прогон миграций и перепроверка
  предположений о конкурентности; SQLAlchemy и Alembic уже служат нужным швом.
