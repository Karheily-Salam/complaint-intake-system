# ADR-005 — Сначала фиксация состояния, потом подтверждение письма

**Статус:** принято

## Контекст

IMAP доставляет «хотя бы один раз». Что-то должно решать, когда письмо
«обработано», и порядок этого решения определяет цену сбоя.

Возможны два порядка:

1. Пометить письмо `\Seen`, затем обработать его.
2. Обработать и зафиксировать транзакцию, затем пометить `\Seen`.

## Решение

Порядок 2. Письмо подтверждается почтовому серверу только после фиксации его
транзакции в базе данных. Ответ отправляется внутри этой транзакции.

## Рассмотренные альтернативы

- **Сначала подтверждать.** Проще — и неверно: сбой между подтверждением и
  фиксацией теряет обращение навсегда. Почтовый сервер считает письмо
  доставленным, а в системе не существует ничего.
- **Двухфазная фиксация между почтовым ящиком и базой.** По IMAP недоступна и
  совершенно несоразмерна задаче.

## Последствия

- Режим отказа — дублирование *работы*, а не её потеря; для клиентских
  обращений это верный компромисс.
- Значит, дубликаты должны быть безвредны, а для этого нужна идемпотентность
  (ADR-007).
- Отправка ответа внутри транзакции означает, что сбой провайдера откатывает
  весь шаг, поэтому система никогда не продвигает переписку, не спросив
  клиента. Цена — сбой после отправки, но до фиксации, может повторить вопрос;
  повторённый вопрос поправим, а тихо замершая переписка — нет.
- Тест проверяет этот порядок напрямую: из независимого соединения
  контролируется, что строка видна в момент подтверждения.
