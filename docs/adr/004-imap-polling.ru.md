# ADR-004 — Опрос IMAP вместо вебхуков или почтового API

**Статус:** принято

## Контекст

Система должна получать почту. Вариантами были провайдер входящих вебхуков
(Mailgun, SendGrid, Postmark), API почтового ящика (Gmail API, Microsoft Graph)
либо обычный IMAP.

На момент принятия решения не было ни домена, ни TLS-сертификата — только
небольшой VPS.

## Решение

Опрашивать почтовый ящик по IMAP с заданным интервалом и отправлять по SMTP,
всё это за интерфейсом `EmailProvider`. Реализовано только средствами
стандартной библиотеки.

## Рассмотренные альтернативы

- **Провайдер входящих вебхуков.** Требует владения доменом и перевода его
  MX-записей на провайдера, плюс публичной HTTPS-точки. Ничего этого не было,
  поэтому вариант был не просто менее удобным — он был недоступен.
- **Gmail API / Microsoft Graph.** Регистрация OAuth-приложения и экраны
  согласия ради одного почтового ящика. Microsoft к тому же отключила базовую
  аутентификацию для личных аккаунтов, так что там это *единственный* вариант,
  но здесь он несоразмерен задаче.
- **Поднять собственный почтовый сервер.** Отклонено сразу: доставляемость,
  борьба со спамом и безопасность дают объём работ, далеко превышающий пользу.

## Последствия

- Работает с любым почтовым ящиком и паролем приложения; домен не нужен.
- Опрос — исходящее соединение, поэтому не нужен ни входящий порт, ни изменение
  правил файрвола.
- Задержка доставки — до одного интервала опроса (около 60 с), что для приёма
  обращений не имеет значения.
- Почтовый ящик фактически выступает очередью входящих с доставкой «хотя бы
  один раз» — поэтому и важна идемпотентность (см. ADR-007).
- Блокирующие библиотеки в асинхронном цикле событий потребовали аккуратности:
  вызовы провайдера выполняются в рабочем потоке и имеют явные таймауты сокета,
  иначе поглощённое файрволом соединение подвесило бы всё приложение.
