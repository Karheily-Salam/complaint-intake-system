# Учения по резервному копированию и восстановлению

«У нас есть резервные копии» и «у нас есть резервные копии, которые
восстанавливаются» — разные утверждения. Эта страница документирует второе, и
описанные ниже учения действительно проводились, а не только записаны.

## Что копируется

База данных приложения: SQLite по пути `/app/data/complaint_intake.db` внутри
контейнера `backend`, сохраняемая в именованном томе Docker `backend_data`. Она
содержит все переписки, письма, обращения, собранные поля и заявки.

Не копируется — либо потому, что воспроизводимо, либо потому, что не должно
перемещаться:

| Нет в копиях | Почему |
|---|---|
| `backend/.env` | Содержит пароль почтового ящика и ключ сотрудника. Хранится только на сервере, права `600`. |
| Образы Docker | Пересобираются из репозитория. |
| Сам почтовый ящик | Принадлежит почтовому провайдеру. Обработанные письма остаются там с флагом `\Seen`. |

## Как снимаются копии

Скрипт `ops/scripts/backup-sqlite.sh`, запускается ежедневно в 03:30 из
crontab пользователя `deploy`.

Он использует **API онлайн-бэкапа SQLite** (`sqlite3.Connection.backup()`),
выполняемый внутри контейнера уже имеющимся там Python, — намеренно *не* `cp` и
не `docker cp`, любой из которых может захватить файл разорванным посреди
записи.

- **Расположение:** `/opt/backups/complaint-intake-system/`
- **Имена:** `complaint-intake-system-ГГГГММДД-ЧЧММСС.db.gz`
- **Хранение:** 14 дней, обеспечивается самим скриптом, который удаляет только
  собственные файлы с временными метками — никогда не живой том.

```bash
# Снять копию вручную
/opt/ops/scripts/backup-sqlite.sh /opt/projects/complaint-intake-system \
    backend /app/data/complaint_intake.db complaint-intake-system
```

**Копий за пределами сервера пока нет.** Всё перечисленное лежит на том же
диске, что и живые данные: это защищает от неудачного развёртывания или
случайного удаления, но не от потери самого хоста. Этот пробел реален и указан
здесь прямо, а не обойдён молчанием.

## Учения

Восстанавливаем в изолированное место и там же проверяем. Ничто из описанного
ниже не затрагивает ни живую базу, ни работающие контейнеры.

### 1. Восстановить копию во временный файл

```bash
cd /tmp && mkdir -p restore-drill && cd restore-drill
cp /opt/backups/complaint-intake-system/complaint-intake-system-<МЕТКА>.db.gz .
gunzip complaint-intake-system-<МЕТКА>.db.gz
mv complaint-intake-system-<МЕТКА>.db restored.db
```

### 2. Убедиться, что файл — целостная база

```bash
sqlite3 restored.db "PRAGMA integrity_check;"     # ожидается: ok
sqlite3 restored.db "PRAGMA foreign_key_check;"   # ожидается: пустой вывод
sqlite3 restored.db "SELECT COUNT(*) FROM tickets;"
sqlite3 restored.db "SELECT version_num FROM alembic_version;"
```

Значение `alembic_version` важно: оно показывает, на какой схеме находится
копия, и тем самым — сможет ли текущий код с ней работать.

### 3. Убедиться, что приложение действительно с ней работает

Целостность — не то же самое, что совместимость: исправный файл на старой схеме
всё равно сломается. Запустите одноразовый контейнер, направленный на
восстановленную копию:

```bash
docker run --rm -p 127.0.0.1:8099:8000 \
  -v /tmp/restore-drill:/restore \
  -e DATABASE_URL=sqlite:////restore/restored.db \
  -e AI_PROVIDER=rule_based -e EMAIL_PROVIDER=mock \
  -e STAFF_API_KEY=drill-only-key \
  complaint-intake-backend:latest

curl -fsS http://127.0.0.1:8099/api/v1/health
curl -fsS -H 'X-API-Key: drill-only-key' http://127.0.0.1:8099/api/v1/ops/stats
```

При запуске применяются ожидающие миграции, поэтому это заодно доказывает, что
копию можно привести к текущей схеме.

### 4. Убрать за собой

```bash
rm -rf /tmp/restore-drill
```

## Восстановление по-настоящему

Только когда живая база действительно потеряна или повреждена:

```bash
cd /opt/projects/complaint-intake-system
docker compose stop backend                      # сначала остановить запись
gunzip -c /opt/backups/.../<файл>.db.gz > /tmp/restored.db
docker compose cp /tmp/restored.db backend:/app/data/complaint_intake.db
docker compose start backend
docker compose logs -f backend                   # миграции, затем «startup complete»
```

Сначала снимите копию *текущего* (сломанного) файла, если есть хоть какая-то
вероятность, что в нём остались данные, которых нет в резервной копии.
